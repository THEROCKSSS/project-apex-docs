01 / FOR PLAYERS

From an invitation to a server.

The intended player journey is simple. A Windows setup EXE, React launcher, desktop shortcut, repair, uninstall and support export have been exercised in the lab. Automatic game provisioning and independent network invitations are still being developed; the steps below describe the complete target experience.

  1. Install Project ApexRun the setup EXE and use the desktop shortcut. Setup checks explain missing prerequisites.
  2. Choose a communityImport the owner’s network invitation. Review who operates it before signing in.
  3. Prepare the gameA compatible build adapter uses an isolated copy of your own installation and records reversible changes.
  4. Browse and playChoose a real server in the native browser. Join authorization belongs to that host; discovery is optional.
Current lab evidence

One full-size Wakistan server, a native browser-to-world join, two basic opposing bots, 26 native earned-XP events totaling 18,000 XP, and a visible native leaderboard entry have been verified. The native menu restored that saved XP as rank 2. Pilot-seat entry and full engine power were observed; an earlier bounded assisted takeoff is recorded separately. Unassisted flight and landing, full master-service egress isolation, and hydration of the server’s in-round native profile remain open checks.

If setup fails

The launcher’s first slice records bounded setup and failure codes and offers a sanitized support report. Preview the report before sharing it. Raw game logs can contain private data and are not part of the public research site.

Removing it

The installer is designed to remove the application and its shortcuts through Windows Settings. The game installation remains separate. Saved application data is preserved unless you deliberately remove it.

02 / FOR HOSTS

Your network. Your rules.

Host a community

Each independent operator should own their accounts, listings, moderation and clan approvals. Players choose which operator they trust. Separate XP on every server is a fixed requirement.

PARTIAL / LOCAL SERVICES

Share a direct invitation

A network invitation identifies the host and compatible service. It must not include an administrator credential. Direct admission should keep working when an optional directory is unavailable.

PLANNED / NETWORK INVITATIONS

Open to the Internet

Public hosting needs verified game/query listeners, host authentication, explicit ingress, resource limits and reconnect tests. Publishing a listing does not automatically make a host reachable.

PLANNED / PUBLIC HOSTING

What already exists

The independent community API implements scoped credentials, per-server earned XP and leaderboards, pending clan applications, administrator approve/reject/suspend decisions and a configurable name blacklist. The private HTTP API now also has a direct server-authorized profile lookup, with server isolation, fresh XP reads, revocation and approved-clan filtering exercised through the real application boundary in tests. That route is not deployed or wired into native admission yet. Username/password login, remote Steam-ticket verification and network federation are not implemented yet.

03 / RESEARCH NOTES

Evidence before conclusions.

The installed Unity/IL2CPP build contains native machine code. A decompiler can help explain it, but that output is not the original source and does not automatically compile into a matching game.

  1. Pin the input. Hash artifacts and state exactly which build and byte regions are measured.
  2. Follow a question. Use REA’s session and function tools, saved metadata and references to trace one behavior and its state changes.
  3. Reconstruct source. Write typed source for a bounded function, recording its dependencies, ABI, compiler, linker and layout.
  4. Compare and exercise. Compile fresh code, compare its bytes with the pinned extent, then run finite behavioral probes. Keep helper code out of the matching total.
  5. Record the gap. Keep unexplained code, data, assets, indirect calls and runtime uncertainty visible. Never replace unknowns with a completion claim.

Concrete findings

Native rank costs

TeamManager.GetXP at RVA 0x133a6d0 supplies rank thresholds. The original save stores prestige, rank, remaining EXP and total score independently. Total XP cannot recover arbitrary original prestige/history.

tools/reconstruction/pint_arithmetic.c
/* Unboxed PlayerStats.Pint operations from the pinned Win64 build.
 * The eight-byte aggregate is passed/returned in an integer register.
 * This is the complete two-field value layout, without a managed object header.
 * A signed increment contributes its raw modulo-2^32 bit pattern.
 * MethodInfo remains an explicit ignored argument. Null this is unchecked.
 */
typedef unsigned int uint32;
typedef signed int int32;

struct Pint {
    uint32 base;
    uint32 additional;
};

__declspec(noinline) void pint_increment(struct Pint *value, int32 delta, void *method_info)
{
    (void)method_info;
    value->additional += (uint32)delta;
}

__declspec(noinline) void pint_reset(struct Pint *value, void *method_info)
{
    (void)method_info;
    value->base += value->additional;
    value->additional = 0;
}

__declspec(noinline) uint32 pint_to_uint(struct Pint value, void *method_info)
{
    (void)method_info;
    return value.additional + value.base;
}

__declspec(noinline) struct Pint uint_to_pint(uint32 value, void *method_info)
{
    struct Pint result;
    (void)method_info;
    result.base = value;
    result.additional = 0;
    return result;
}
tools/reconstruction/pint_format.c
/* PlayerStats.Pint.ToString caller from the pinned Win64 build.
 * Runtime metadata initialization, UInt32 boxing, String.Format and managed
 * literal/type objects are explicit external dependencies with zero credit.
 * No managed object allocation or format implementation is reconstructed here.
 */
typedef unsigned char uint8;
typedef unsigned int uint32;
struct Pint { uint32 base, additional; };
struct RuntimeClass;
struct ManagedObject;
struct ManagedString;
extern uint8 pint_format_guard;
extern const uint32 pint_format_usage;
extern struct RuntimeClass *pint_uint32_type;
extern struct ManagedString *pint_format_literal;
void initialize_metadata(uint32 usage);
struct ManagedObject *box_uint32(struct RuntimeClass *type, uint32 *value);
struct ManagedString *format_three(struct ManagedString *format,
    struct ManagedObject *first, struct ManagedObject *second,
    struct ManagedObject *third, void *method_info);

__declspec(noinline) struct ManagedString *pint_to_string(struct Pint *value, void *method_info)
{
    uint32 base, additional, total;
    struct ManagedObject *first, *second, *third;
    (void)method_info;
    if (!pint_format_guard) {
        initialize_metadata(pint_format_usage);
        pint_format_guard = 1;
    }
    base = value->base;
    first = box_uint32(pint_uint32_type, &base);
    additional = value->additional;
    second = box_uint32(pint_uint32_type, &additional);
    total = value->additional + value->base;
    third = box_uint32(pint_uint32_type, &total);
    return format_three(pint_format_literal, first, second, third, 0);
}
tools/reconstruction/progression_arithmetic.c
/* Complete branch-free leaves from the pinned build, not entire class layouts.
 * PlayerProgess is a managed object; Pint is an unboxed eight-byte value type.
 * Unsigned arithmetic defines the native wraparound without signed C overflow.
 * MethodInfo is present in the Win64 ABI and unused by these native bodies.
 * Roots are unchecked in the original; a null receiver is outside this proof.
 */
typedef unsigned char uint8;
typedef unsigned int uint32;

struct ProgressRank {
    uint8 unknown_prefix[0x88];
    uint32 prestige;
    uint32 rank;
};
struct ProgressRounds {
    uint8 unknown_prefix[0x58];
    uint32 wins;
    uint32 losses;
};
struct Pint {
    uint32 base;
    uint32 additional;
};

__declspec(noinline) uint32 full_rank(const struct ProgressRank *progress, void *method_info)
{
    (void)method_info;
    return progress->prestige * 200u + progress->rank;
}

__declspec(noinline) uint32 rounds_played(const struct ProgressRounds *progress, void *method_info)
{
    (void)method_info;
    return progress->losses + progress->wins;
}

__declspec(noinline) uint32 pint_value(const struct Pint *value, void *method_info)
{
    (void)method_info;
    return value->additional + value->base;
}

05 / CONTENT & GAMEPLAY

Extend one verified seam at a time.

Rules and game modes

The installed community server API accepted a real native Wakistan snapshot and delivered a round-start callback to our bounded observation host. Its TCP gameplay connection is separate from our HTTP progression service. Player lifecycle hooks and a small infection/tag mode still need actual gameplay tests.

NATIVE CONNECTION VERIFIED / MODE NOT IMPLEMENTED

Maps, models and vehicles

New maps, weapons, vehicles, helicopters and mechanics need verified asset and code integration. A server API is not an arbitrary content loader. No new content loader is shipped yet.

PLANNED

Compatible downloads

Content should declare its build, dependencies and hashes, let players review the source, and support rollback. Signing identifies a publisher; it does not prove a package is safe.

PLANNED

A full game rebuild and the ability to turn it into another game are not available. Recovered function source is one ingredient; a complete build also needs generated code, dependencies, data, resources and layout. New content must use assets its authors can distribute.

06 / FOR DEVELOPERS & AGENTS

Leave the next person a reproducible result.

Start from an evidence question

Use the pinned artifact identity and existing saved analysis first. Read the project handoff and applicable instructions. Avoid duplicate analysis sessions and unexplained runtime patches.

Test the actual boundary

Reproduce a bug, change one seam, rerun its behavior and compare the exact artifact. Synthetic fixtures are useful but do not establish that a native server joined or a helicopter flew.

Improve code without losing proof

Keep reconstructed function sources, toolchain pins and receipts linked. A cleaner equivalent implementation may cease to match the original bytes; report semantic improvements separately.
